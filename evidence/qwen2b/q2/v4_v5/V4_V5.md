# V5 and the V4mix ladder — W8 modeled, scored and priced (Track Q task 9)

The study's last measurement task. It adds an 8-bit weight format to the
frozen wire law, scores **five** new points against the same corpus /
checkpoint / window every other Track Q point used, and produces the byte and
throughput columns of the gate-D table from a calculator that reproduces the
feasibility study's numbers to the byte.

**Every number below is derived by a committed script from a committed
artifact.** `v4_v5_table.py` prints the whole ladder (output:
`v4_v5_table.txt`), `ref/scripts/bytes_per_token.py` the bytes/fit/tok-s
columns (`bytes_table_2b.log`), `ref/w4a8_ref.py` the format facts
(`selftest_w4a8_w8.log`). All compute on **snoke**, per Q8's host ruling;
darthplagueis was used for orchestration only.

### 2.1 The quantizer, and the one honest asymmetry

`quantize_weights8` is `quantize_weights` with the weight range changed from
[-8,7] to **[-127,127]** (symmetric — -128 is never emitted, so every
representable weight has a representable negation). The scale encoding is
untouched: one uint16 mantissa per group, one shared exponent per matrix,
value `m * 2^(e-15)`, so **Task 4's arbitrated dequantization formula applies
verbatim** — re-checked for W8 against `matvec_y32` in `perplexity_eval
--selftest` section D4 (max |y32 − dequant| = 0.500 lsb of the final
rounding, max rel 8.3e-07).

Two deliberate deviations from the W4 twin, both toward the *production*
path rather than the legacy one: the arithmetic is float64 regardless of
input dtype (what `quant_linear_mse` does), and a `rowchunk` argument keeps
the 248,320-row tied head off a 4 GiB temporary (what `quant_linear_big`
does). Chunking is asserted bit-identical, at three chunk sizes, on five
shapes and four seeds.

**The asymmetry, stated up front:** W4 in this study uses the production
**MSE-searched** group scale (`layer_fixed.quant_linear_mse`); W8 uses the
**max|W_g|/127** rule, with no search. This is the conservative direction —
a search could only improve W8 — and the size of what is left on the table is
bounded by the measurement itself: V5's *entire* damage is +0.014380 PPL, so
no better W8 rule can move the gate-D picture by more than that. It is not
worth a second quantizer.

### 3.1 V5 is nearly lossless, and the rerun is bit-identical

The two V5 processes agree on `nll_sum` to the last bit (61676.15431976318),
which is stronger than the study's six-decimal convention and stronger than
Q8's cross-host V3 comparison could be. For scale: W8's damage across the
**whole model** (+0.014380) is only 1.35x the damage Task 7 measured from
putting the single *least* sensitive class, `dn_out`, into W4 g64 on its own
(+0.010640).

### 3.2 The V4mix ladder against Task 7's arithmetic prediction

Task 7 predicted each mixed map as "V2 minus the promoted classes'
one-at-a-time ΔPPL", explicitly labelled arithmetic rather than measurement.
It holds up remarkably well, and where it fails it fails in the *favourable*
direction:

| k | promoted | predicted | measured | error |
|---|---|---|---|---|
| 1 | gate_up | 13.274761 | **13.275505** | **+0.000744** |
| 2 | +lm_head | 13.001903 | **12.975961** | −0.025942 |
| 3 | +dn_in | 12.816223 | **12.720237** | −0.095986 |

Two effects with opposite signs are folded into that error. The prediction
treats a promoted class as *undamaged*, so W8's own residual (whole-model:
+0.014380) pushes measured PPL up; Task 7's measured super-additivity
(+0.075 joint vs sum-of-parts) pushes it down, because pulling the biggest
classes out of the W4 set removes more than their solo deltas. At k=1 the
two nearly cancel to 0.0007; by k=3 super-additivity wins by 0.096.

**The ladder is real, monotone, and irrelevant** — see §6.

## 4. The bytes/token calculator

`ref/scripts/bytes_per_token.py` computes, from the model config and a
precision map, `SUM over the 187 matvec images of nrows * row_stride(K,g)`
(or `row_stride8` for W8) — the production row format with beat padding in,
never the ideal bits/weight. A decode step reads every image exactly once,
so **per-token traffic IS the packed footprint**, which is why the same
arithmetic answers the DDR-fit question.

Validated four ways, all hard asserts in `--selftest`:

1. **The two feasibility numbers, to the byte**: 0.8B W4 g128 =
   **417,435,648**, 2B W4 g128 = **996,282,368**.
2. **Five committed `perplexity_eval` runs, per class**: 0.8B w4g128, 2B V1,
   V2, **V5 and V4mix top-3** — 7/7 classes agree on matrix count, weight
   count *and* packed bytes in every one. Those totals came from the real
   checkpoint's tensor shapes through `packed_bits`, so this also proves the
   config-derived inventory matches the actual model matrix by matrix. (This
   check takes its plan *from* each json's `inject_resolved`, so it is not
   where `--map` is shown to agree with `--inject`: that is
   `v4_v5_table.py:72-74`, which asserts each hand-written `--map` spec in
   the ladder resolves to exactly the plan that run scored.) The last two
   rows are the same check for the **W8** row law.
3. **The 4-channel row split** reproduces `MOVER_NORM.md` §3.1's
   busiest-channel beat counts exactly — 0.8B `[1643280, 1629456, 1624848,
   1624848]`, 2B `[3915664, 3889552, 3880848, 3880848]` — including the LM
   head's `ilv_chunks` interleave.
4. **The W8 law**: `row_beats8` is exactly `2x` the W4 weight beats with the
   **same** scale beats, on every K the two models use.

Consequence worth stating because it is counter-intuitive: **W8 is 1.944x
its W4 g128 twin at 2B, not 2.000x** (1.901x at 0.8B). *(Mind the
denominator: 1.938 is the table's x**V2** column, and V2 is g64, whose rows
carry an extra scale beat at K=6144. Against g128 the 2B ratio is
1,936,920,576 / 996,282,368 = 1.944; the 0.8B figure quoted here is already
against g128.)* The weight side doubles; the
scale side does not; and the beat-padding overhead *falls* (8.237 b/w
against an 8.125 ideal, +1.4 %, where W4 g128 pays +2.7 %).

## 5. DDR fit — V5 does not fit, and nch=4 does not rescue it today

The weight window is **1,280 MiB per channel** (`W_BASE 0x1000_0000` ..
`EMB_BASE 0x6000_0000`), and `sw/layer_test.py:plan_weights` *asserts* the
pack ends below `EMB_BASE`. Packing each image back to back with
`WID_ALIGN` = 4096:

| variant | nch=1 | | nch=4 | |
|---|---|---|---|---|
| V1 / V2 / V3 / V4gptq | 950-953 MiB | 74 % OK | 239-240 MiB | 19 % OK |
| V4mix top-1 | 1,241 MiB | 97 % OK | 312 MiB | 24 % OK |
| **V4gptq + gate_up W8** | 1,241 MiB | 97 % OK | 312 MiB | 24 % OK |
| V4mix top-2 | 1,484 MiB | **116 % — DOES NOT FIT** | 374 MiB | 29 % OK |
| V4mix top-3 | 1,628 MiB | **127 % — DOES NOT FIT** | 410 MiB | 32 % OK |
| **V5** | **1,847 MiB** | **144 % — DOES NOT FIT** | 465 MiB | 36 % OK |

**The nch=4 column is a BYTES result, not today's fit.** The per-channel byte
counts are right, but the host does not pack per channel: `plan_weights`
takes no `nch` and accumulates **full image footprints** from `W_BASE`, and
`sw/seq_run.py:plan_weight_split` then places each channel's slice at
`wbase_of[wid] + r0*stride` — inside the *whole* image's span. So every
channel's map today reserves the whole image, the pack is nch-independent,
and **V5 trips `plan_weights`' assert at nch=4 as well as at nch=1**.
Realizing the nch=4 column needs per-channel bases plus per-chunk rebasing
of the ILV-placed LM head (whose channel rows are strided, not contiguous) —
a host/emitter prerequisite that belongs in the W8 cost, and is recorded in
`W8_SKETCH.md` §6.1. **No re-map is proposed here** (the brief's
instruction, and the right call: the address map is Track R's). The finding
is that any W8 variant beyond top-1 needs *either* a bigger window or that
per-channel repack, and V4mix top-1 clears the current single-span pack by
only 3 %. Two adjacent facts fall out and are recorded rather than acted on:

* the **embedding table at 2B is 970 MiB** (248,320 rows x 4096 B), against
  the 485 MiB `sw/hwmap.py:419-421` describes for 0.8B's 2048 B rows. It
  still fits — it grows into the documented FREE tail and ends at
  `0x9CA0_0000` — but the map comment is 0.8B-specific and should say so.
* per-token embedding *traffic* is one row: 4,096 B, i.e. 0.0002 % of the
  weight traffic. It is excluded from the headline for that reason (Task 7's
  convention).

## 6. Throughput — and the correction that matters

Modeled with `MOVER_NORM.md`'s per-row law: only the **matvec** bucket moves
with precision (MOVX/MOVY/LDC/CSRWR move activations, results and constants;
the MVGO record count follows the row split, not the row stride), so
`step = matvec(r) + movers 15.994 + layer 17.4` ms at nch=4, with `r` over
MOVER_NORM's calibration-free bracket [1.000, 1.131] ui-cyc/beat.

(Every cell below is `v4_v5_table.txt`'s "step decomposition" block, not
retyped arithmetic. V1 is 13.05 .. 14.76 / 46.44 .. 48.15 — close to V2 but
not equal, because g64 adds one scale beat per row at K=6144 (`mlp.down`,
24 of the 187 images); at K=2048 the two modes have identical rows.)

| variant | matvec ms (r lo..hi) | step ms | **tok/s** | vs V2 |
|---|---|---|---|---|
| V2 / V3 / V4gptq | 13.09 .. 14.80 | 46.48 .. 48.20 | **20.75 - 21.51** | — |
| V4mix top-1 / **V4gptq+gate_up W8** | 17.02 .. 19.25 | 50.41 .. 52.64 | 19.00 - 19.84 | −8 % |
| V4mix top-2 | 20.40 .. 23.08 | 53.80 .. 56.47 | 17.71 - 18.59 | −15 % |
| V4mix top-3 | 22.38 .. 25.31 | 55.77 .. 58.70 | 17.04 - 17.93 | −18 % |
| **V5** | 25.37 .. 28.69 | 58.76 .. 62.08 | **16.11 - 17.02** | **−21 to −22 %** |

**Doubling weight traffic does not halve throughput.** The dispatch framed
V5 as costing "~half the tok/s"; the modeled decomposition says **−21 to
−22 % over the `r` bracket** (−20.9 % at r=1.000, −22.4 % at r=1.131),
because the matvec bucket is only ~28 % of the modeled step. The sensitivity
is bounded: with the (unverified) 17.4 ms layer bucket removed entirely, the
worst case is **−31 %**, and the mover bucket alone (16 ms) makes anything
near −50 % arithmetically impossible.

The absolute tok/s figures inherit MOVER_NORM's caveats — chiefly the 17.4 ms
layer term, which that document flags as the widest uncertainty in the line
and which is *not* remeasured here. The **relative** column is much more
robust: it depends only on the matvec share, and it is quoted as a range
over both `r` and the layer term above.

## 7. The gate-D reading

Plotting quality against bytes, **three** points are on the frontier — and
the middle one is a composition this task added, not a plan variant:

* **V4gptq — 42.6 % of the gap left, at 1.000x bytes and 1.000x tok/s.**
  Free, in DDR and on the wire; costs image-build time and the emitter
  wiring Q8b already landed.
* **V4gptq + `gate_up` at W8 — 27.9 % left, at 1.302x bytes and 0.92x
  tok/s**, and it still fits the current pack (97 % of the window). §7.1.
* **V5 — 1.0 % of the gap left, at 1.938x bytes and 0.78-0.79x tok/s**,
  and needs either a bigger weight window or the per-channel repack of §5.

Every V2-based mixed map is dominated:

* **V4mix top-2 (12.975961) is WORSE than V4gptq (12.941240)** while
  spending 556 MB more per token. The whole mixed-precision middle at k≤2 is
  strictly inferior to a free quantizer.
* V4mix top-3 (12.720237) *is* better than V4gptq, by 0.221 PPL — but it
  costs 708 MB more per token, a weight pack that overflows the window,
  −18 % tok/s, **and** an
  emitter that must learn per-class precision (a mixed image set is
  materially more generator work than V5's uniform one, `W8_SKETCH.md` §4)
  — and §7.1 reaches the *same* PPL for 302 MB and a single channel.
* Marginal rate against V2: **300 MB per PPL point** for the composed point,
  against 644 / 724 / 691 for V2-based top-1/2/3 and 678 for V5.

So the study's decision table has four live rows: **V2** (the baseline),
**V4gptq** (free quality, ship it either way), **V4gptq + gate_up W8** (the
cheap intermediate, +30 % bytes, −8 % tok/s, no map change) and **V5**
(near-lossless, −21 to −22 % tok/s, needs RTL *and* the §5 repack). The V2-based mixed maps
are the *demonstration* that the middle is not free — which is what Task 7
predicted from bytes alone, now measured — and they are not candidates.

### 7.1 The composed point: V4gptq base + `gate_up` at W8

`all:w4g64gptq,gate_up:w8g128` — same ladder step as V4mix top-1 with one
variable changed (the W4 rule underneath). Added after V5 landed, because
with GPTQ recovering 57 % of the gap for free the interesting mixed point is
no longer "V2 + W8".

| | PPL | bytes/token | xV2 | MB per PPL point vs V2 | pack fit | tok/s |
|---|---|---|---|---|---|---|
| V4gptq (base) | 12.941240 | 999,428,096 | 1.000 | free | 74 % | 20.75-21.51 |
| V4mix top-1 (V2 base) | 13.275505 | 1,301,417,984 | 1.302 | 644 | 97 % | 19.00-19.84 |
| **V4gptq + gate_up W8** | **12.736774** | 1,301,417,984 | 1.302 | **300** | **97 %** | 19.00-19.84 |
| V4mix top-3 (V2 base) | 12.720237 | 1,707,282,432 | 1.708 | 691 | **DOES NOT FIT** | 17.04-17.93 |
| V5 | 12.360678 | 1,936,920,576 | 1.938 | 678 | **DOES NOT FIT** | 16.11-17.02 |

**Composing wins, and it is not close.** The same +302 MB/token that bought
0.469 PPL on the V2 base buys 0.204 on the GPTQ base — a smaller absolute
step, because GPTQ has already repaired much of `gate_up`'s damage — but it
lands at **12.736774, i.e. V4mix top-3's quality (12.720237) for top-1's
bytes**, and unlike top-3 it still fits a single channel. Per PPL point it
costs **300 MB against 644-724 MB** for every V2-based mixed map and 678 MB
for V5.

This makes the V2-based V4mix ladder obsolete as a *candidate* (it survives
as the controlled measurement of how mixed precision behaves), and it gives
gate D a real intermediate option that the plan did not anticipate:
**GPTQ everywhere + W8 on the single most sensitive class**, at +30 % bytes
and −8 % tok/s, with no address-map change.

**Rerun stamp.** As a live gate-D row it gets the study's rerun convention:
a second process reproduces **12.736774** — agreement to six decimals, but
`nll_sum` 62411.334332 against 62411.333758, i.e. **9.2e-09 relative, not bit
identical**. The cause is known and is not the measurement: the two processes
ran at **different thread counts** (8 and 10), and Q8b established that
torch's threaded reduction order — not the quantizer — is what breaks bit
identity across thread counts. The five matched-thread rerun pairs of §9.6
(8 threads on both sides) ARE bit-identical — including the three mixed
V4mix maps — so this is a thread-count artifact, not something about mixing
precisions. Anyone repeating this one
should pin `OMP_NUM_THREADS`.

Two caveats, stated because they are the reasons this is one run and not
four: only k=1 was measured on the GPTQ base (k=2/3 are ~35 min each and the
frontier question is answered), and it inherits every V4gptq caveat from
`GPTQ.md` — calibration dependence, the emitter wiring, and the doubled
image-build time (1,634 s here, 1,443 s on the rerun).

## 8. Why there is no W8+GPTQ point

Out of scope by argument, not by schedule. GPTQ re-rounds against the
*quantization residual* of neighbouring columns, and at 8 bits that residual
is 15-18x smaller than at 4 (measured). V5's total damage is +0.014380 PPL;
the entire headroom any better W8 quantizer could recover is inside that,
i.e. inside the noise of what this harness resolves. A W8+GPTQ run would
cost a full calibration + scoring cycle to measure a number that cannot
change a gate-D decision. Recorded in `W8_SKETCH.md` §5 as well, because
that is where a reader looking for "what else could we do to W8" will land.

## 9. Concerns / open items

1. **No RTL exists and `W8_SKETCH.md` is a sketch, not a design.** It fixes
   the wire format precisely (and the host side is committed and self-tested),
   identifies every CSR/width that moves, and finds one real constraint —
   `ng` must keep meaning `K//128` or the 6-bit SHAPE field overflows at
   K=6144 — but it does **not** price the lane array (64x 8x8 against 128x
   4x8). That needs one synthesis run of a parameterized `matvec_engine`.
2. **V5 does not fit the weight window — at any `nch`, as the host packs
   today.** `plan_weights` takes no `nch` and accumulates full image spans;
   `sw/seq_run.py:plan_weight_split` slices each channel's rows *inside* that
   span, so the 36 % per-channel figure is bytes, not a fit, and V5 trips the
   same assert at nch=4 as at nch=1. Stated, not fixed (the brief's
   instruction). Two independent ways out, both Track R's call: move the
   window, or teach the host/emitter per-channel image bases plus per-chunk
   rebasing of the ILV-placed LM head. The latter is now part of the W8
   costing (`W8_SKETCH.md` §6.1).
3. **The tok/s column inherits the 17.4 ms layer term**, which MOVER_NORM
   itself flags as unverified. The relative penalty is bracketed (§6); the
   absolute numbers are not better than that term.

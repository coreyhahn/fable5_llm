## 0. What V3 is

`layer_fixed.quant_linear_mse` picks each group's INT4 scale by a 17-point
grid search that minimises the group's reconstruction error. V3 changes the
OBJECTIVE of that search and nothing else:

    plain (V2)   argmin_s  sum_k (Wq[k]*s - W[k])^2
    salience(V3) argmin_s  sum_k (Wq[k]*s - W[k])^2 * salience[k]^2

where `salience[k]` is the mean |activation| on input channel `k`, measured
by `ref/calib_stats.py` over the CALIBRATION corpus. It is the diagonal
approximation of `||(W - Wq) diag(salience)||_F` — error on a column that
multiplies a large activation costs proportionally more.

**The wire format does not move.** `w4`/`m`/`e`/`sh`/`g` keep their shapes
and dtypes, so a V3 image is byte-for-byte a legal `w4g64` DDR image and no
RTL, row format or byte budget changes. V3 and V2 are recorded at the
**same 6.752534 bits/weight** in Table A — this is free quality, not a
bit-rate trade.

This file was produced on darthplagueis **inside the §6 fault window**, and
it feeds both otherwise-clean snoke runs of §7. That chain is closed
separately in §6 ("The calibration npz was also a fault-window artifact"):
regenerated on snoke, worst relative delta **4.191e-07**, zero channels over

usable equality test — `np.savez` embeds zip timestamps and the metadata
carries wall-clock fields — so the comparison is on the vectors and on the
quantized images.

The 187 = 187 identity is a real check, not bookkeeping: the collector hooks
every `nn.Linear` the model instantiates and the required list is derived
independently from the geometry (6 full-attention layers x 4 + 18 DeltaNet
layers x 5 + 24 MLP x 3 + the tied head). A model change that added a matvec
the W4 engine does not cover would break it loudly.

The LM head is not an `nn.Linear` here (`perplexity_eval` computes
`hs @ head_w.T` by hand, exactly as the HW does), so its input is the FINAL
NORM's output and that module is hooked instead, under the key `lm_head`.

### Where the weighting has anything to act on

A uniform salience is provably a no-op (§3), so the gain can only come from
classes whose input channels differ in magnitude. `salience_profile.txt`:

| class | mats | max/mean | p99/median | CV |
|-------|------|----------|------------|-----|
| qkv | 18 | 31.6 | 4.0 | 0.92 |
| o_proj | 6 | 18.2 | 5.9 | 1.20 |
| gate_up | 48 | 26.4 | 3.3 | 0.72 |
| down | 24 | 12.6 | 3.0 | 0.45 |
| dn_in | 72 | 30.7 | 4.0 | 0.89 |
| dn_out | 18 | 18.4 | 6.9 | 1.16 |
| lm_head | 1 | 15.4 | 3.2 | 0.62 |

(median over the matrices of each class.) Every class is skewed — 12-32x
between the loudest channel and the mean — so the weighting bites
everywhere rather than in one hot spot. That predicts a broad, moderate
gain rather than a dramatic one, which is what §4 measures.

## 2. One production quantizer, two harnesses (Step 2)

The binding constraint on this task was that V3 IS the production quantizer,
not a study-only copy. It is a ~5-line change inside the existing scale
search of `layer_fixed.quant_linear_mse`, plus the identical change mirrored
into `gen_model_script.quant_linear_big` (the row-chunked variant the
248320-row tied head needs).

Both harnesses reach that one implementation:

* `perplexity_eval.py --inject all:w4g64s --calib-stats FILE` — the float
  weight-damage score;
* `fidelity_check.py` with **`FABLE5_CALIB_STATS=FILE`** — the fixed-point
  FxRunner. The env var is read ONCE at import in `layer_fixed`, exactly
  like `model_select.FABLE5_MODEL`, and `quant_layer` grew a `layer_idx` so
  each matrix can be given its own vector.

Three guards keep those two paths from drifting apart:

1. `gen_model_script._selfcheck` asserts `quant_linear_big == quant_linear`
   bit-for-bit **including with salience** (uniform and skewed), so row
   chunking stays orthogonal to the weighting.
2. `perplexity_eval --selftest` D2 asserts the 16 salience keys this harness
   asks for are EXACTLY the ones `calib_stats`/`fidelity_check` produce, in
   **both directions**. The two harnesses derive that key by independent
   code (HF parameter name vs `layer_fixed`'s internal weight names); if they
   disagreed, one would silently weight a matrix by another channel's
   salience and both would still appear to work.
3. A missing key is a hard `SystemExit`, never a silent fall back to plain
   MSE — a half-weighted model is a number nobody could interpret.

## 3. The invariance test (Step 3) — written and run BEFORE any scoring

`layer_fixed._salience_invariance`, run by `ref/layer_fixed.py`:

```
  salience: None == arg-absent == ones(K) (bit-identical, g=128 and 64) OK
  salience: FABLE5_CALIB_STATS unset -> every lookup is None (quant_layer inert) OK
  salience: plumb ON re-scales 8/8 DeltaNet+MLP matrices (0 shifted the
            shared exponent), wire format (shape/dtype/sh/g/keys) unchanged OK
```

* **`salience=ones(K)` is EXACTLY `salience=None`.** The weights are
  normalised to mean 1, and both `1.0/1.0` and `x*1.0` are exact in
  IEEE-754, so uniform weighting reduces to the frozen objective with no
  rounding difference at all. Every frozen artifact flows through this
  quantizer; if that were only approximately true the whole 0.8B image set
  would have moved.
* **Unset env == byte-identical.** With `FABLE5_CALIB_STATS` unset every
  lookup returns None and `quant_layer` is inert, so no frozen 0.8B flow can
  pick the feature up accidentally. Bad salience (wrong length, all-zero,
  NaN, negative) is rejected; a missing `layer_idx` with the plumb ON is a
  loud error, not a silent no-op; the max-rule quantizer refuses salience
  outright (it has no scale search to weight).
* Wire format is asserted on shapes, dtypes, `sh`, `g` and the key set. `e`
  is DATA (the shared exponent), so it is reported rather than asserted —
  0/8 matrices moved it here.

## 6. THE HOST FAULT ESCALATED — READ THIS BEFORE THE NEXT CAMPAIGN

`../v1_v2/DECOMP.md` §3.1 documented an impossible assertion trip on
darthplagueis, twice, "unreproduced, under sustained load". **In this task it
happened six times in one working day, on a quiet host, twice inside the
frozen 0.8B regen gate with the salience plumb OFF, and once it killed the
process with SIGSEGV.** The recommendation that section made — a memtest /
under-load arithmetic soak before the next long numeric campaign — is no
longer a nice-to-have.

### The guard cannot trip on correct arithmetic — now proven at dtype level

`ref/w4a8_ref.py:161` is `assert np.abs(acc).max() < (1 << 31)` where

    acc = (w4 * x8).sum over g terms,  w4 and x8 both int8 arrays

so `|acc| <= g * 128 * 128`, which is **1048576 at g=64 — 2048x below the
guard — for ANY int8 content whatsoever.** This is stronger than DECOMP's
argument (which used the legal `w4 in [-8,7]` range, ceiling 65024): even
arbitrary garbage in either operand cannot reach 2^31. No data, no
`res_scale`, and no quantizer rule can make this assertion fire correctly.

Run 6 also raises the count: **six occurrences in one working day on this
host**, two of them in the frozen 0.8B regen gate.

Run 1 is the load-bearing one: **the salience plumb was OFF** (env unset,
0.8B, a code path proven byte-identical to HEAD by the frozen-flow guard),
and its re-run reproduced the frozen sha exactly. The fault therefore exists
independently of everything this task added. Runs 2 and 3 aborted at
*different call sites* from identical deterministic inputs — DECOMP §3.1's
point 4, reproduced.

### Run 4's census is the new evidence

`guarded_matvec_wrapper.py` (committed here, same precedent as DECOMP's
`diag_s16_wrapper.py`: it monkeypatches nothing in the repo and removes no
assertion) audits the operands in place at each trip and retries. Every one
of the 36 events looked like this:

    shape (8192,2048) g=64 sh=6
    w4 int8 [-8,7]      <- legal INT4 range, not corrupted
    x8 int8 [-95,110]   <- legal
    m  uint16 [999,12563]
    acc_bound 56320     <- the ceiling implied by THESE operands
    guard 2147483648    <- 38000x higher
    retry OK; independent re-reduction agrees=True  |acc|max=2409

i.e. the operands were in range, the arithmetic ceiling for them was five
orders of magnitude below the guard, the identical call succeeded on retry,
and an **independently ordered re-reduction** (`np.einsum` instead of
broadcast-multiply-sum) agreed with the retry bit-for-bit.

Exact counts, recounted from `fixed_v3_g64_S4_dp_killed.log`:

* **36 trips over 35 DISTINCT calls** — 35 at `attempt 0` plus one at
  `attempt 1`, i.e. a single call that tripped twice before succeeding.
  There are correspondingly **35 `agrees=True` verifications and 0
  disagreements** (one per distinct call, not 36).
* Shape distribution — **not** confined to one matrix:

  | shape | trips | what it is at 2B (H=2048) |
  |-------|-------|---------------------------|
  | (8192, 2048) | 16 | LM-head row chunk |
  | (6144, 2048) | 16 | `mlp.gate` / `mlp.up` (FFN 6144) or DeltaNet `in_proj_qkv` (2·2048+2048) |
  | (4096, 2048) | 3 | **`self_attn.q_proj`** — gated, 2·NQ·HD = 2·8·256 |
  | (2048, 2048) | 1 | `self_attn.o_proj`, or DeltaNet `in_proj_z` / `out_proj` |

  Only **16 of 36** are the LM-head chunk. The events span a **4x range of
  allocation size** (2048 to 8192 rows) **and three different block types** —
  full attention (`q_proj`, and `o_proj`/DeltaNet at 2048), the FFN/DeltaNet
  input projections, and the tied head. The fault is therefore
  **location-nonspecific**: it does not single out the largest reduction, it
  is not confined to one block, and it does **not** localise to a particular
  buffer or DIMM. An earlier draft claimed all 36 were on the head and
  inferred "a marginal DIMM would show up here first"; that inference was
  unsupported by the log and is **withdrawn**. (That draft also glossed
  (4096, 2048) as a DeltaNet projection — it is `q_proj`; DeltaNet's shapes
  at 2B are 6144, 2048 and 16 rows.)

### Run 4 died of SIGSEGV inside numpy — OOM is excluded

The kernel log names it exactly (`journalctl -k`):

    Aug 13 13:57:28 darthplagueis kernel: python3[528003]: segfault at 1d
      ip 000074b947b382ad sp 00007fff8b09bfe0 error 6 in
      _multiarray_umath.cpython-313-x86_64-linux-gnu.so[1a92ad,...]
      likely on CPU 1 (core 1, socket 0)

which matches the log's last write (13:57:22) and the process's
disappearance. `segfault at 1d` is a near-null (corrupted) pointer
dereference **inside numpy's core array module**; `error 6` is a user-mode
write to a non-present page.

**OOM is excluded, not merely thought unlikely.** `journalctl -k --since
2026-08-11` reports **zero** `oom-kill` / `Out of memory` events, and the
death is explicitly logged as a segfault instead. This mattered: the
wrapper's `np.einsum` re-reduction adds ~134 MB of int64 temporary per event
on top of production, so OOM was a live alternative with a *different*
remedy (bound the shim's memory rather than test the hardware). The kernel
log rules it out, so the memory-integrity remedy stands.

Two honest limits on the diagnosis. EDAC and in-kernel MCE decoding are
loaded on this host and report **no** correctable/uncorrectable errors in the
window — which is **not** exculpatory, because on non-ECC DIMMs EDAC reports
nothing by design. And "likely on CPU 1 (core 1, socket 0)" is the kernel's
own hedge, recorded but not relied on. Two symptoms — wrong int64 reduction
results, and a corrupted pointer inside the same library — are jointly
consistent with memory or CPU corruption; this evidence does **not**
distinguish which.

reproduces the PPL to **all six published decimals** and `nll_sum` to

different interpreter and a different torch build. That is what closes it.

wrapper's census is reported alongside every fixed-point number. **When
`events=0` the wrapper is a pure pass-through** (every call returned from the
unmodified production function on its first attempt), so a zero-event run is
bit-identical to an unwrapped one.

| group scales differing | **4 of 29394944 (0.000014%)** |
| INT4 nibbles differing | **7 of 1881276416 (0.00000037%)** |

The head is compared too, not skipped: it is the largest matrix in the model
and carries salience in every V3 run, so leaving it out would have left the
biggest single contributor unchecked. It needs the row-chunked
`gen_model_script.quant_linear_big` (the checkpoint stores it once as the
tied `embed_tokens.weight`, not as a body parameter), and it lands one group
scale different out of its 7.9 M — the same near-tie effect as the three body
matrices.

**The npz is not corrupted.** A wrong reduction baked into a salience vector
would be a gross single-channel outlier; what is actually there is a uniform
~1e-7 spread, which is simply two different torch builds (2.6.0+cu124 vs
2.12.0+cpu) summing a float32 forward pass in different kernel/threading
orders. The three residual image differences are the 17-point alpha search
landing on a **near-tie** and flipping to the adjacent candidate under a
~1e-7 perturbation — expected behaviour of a discrete grid search, quantified
above, and far too small to move any number in §4 or §7.

Stated precisely, because the earlier draft's framing would have over-claimed:
the V3 images are **not** exactly independent of which host produced the
calibration; the dependence is 4 group scales in 29.4 million and 7 nibbles
in 1.88 billion.

**Recommendation to the controller (their hardware, their call):** memtest86+
and an under-load int64 soak on darthplagueis before it is trusted with
another numeric campaign; until then, treat Track Q compute as snoke work.
Task 8b (GPTQ-lite) must not run there at all — error feedback would
propagate a silent wrong reduction into the weights instead of tripping a
guard.
